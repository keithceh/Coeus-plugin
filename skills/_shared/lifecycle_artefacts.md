# project-lifecycle — Inputs, Outputs, Artefacts Index, Per-Update Telemetry Notes (shared)

> Shared spec for the four artefact-management features (v1.3.0): Inputs list,
> Outputs list, `artefacts_index.md`, and the single append-only
> `_telemetry/log.md`. All four files are created ONCE at kickoff and
> updated in place thereafter — no timestamped duplicates.
> Loaded by `project-lifecycle` Sub-B (handover), Sub-C (audit), Sub-D (close).

---

## 1. Inputs list — §4a of the handover note

Every input the LLM was given (source files, briefs, references, supplied
data, pasted prompts kept as text). Tracked to make the inputs ↔ outputs
trace reconstructible in the next session.

Format (Markdown table):

```markdown
## 4a. Inputs

| File / Source | Location | Provided by | Used by | Notes |
|---|---|---|---|---|
| `[name]` | `[path or URL]` | user / web / prior session | `[skill or task]` | one-line description |
```

Rules:
- An input is anything Claude **read** but did not **produce**.
- A pasted prompt is an input — file it as `pasted_prompt_<n>.txt` in `Outputs/_inputs/` if it survived more than one exchange.
- URLs count. Record the URL and the date fetched.

---

## 2. Outputs list — §4b of the handover note

Every artefact the LLM **produced** this project — code, docs, plans, reports, scripts, diagrams.

Format:

```markdown
## 4b. Outputs

| File | Location | Produced by | Status | Description |
|---|---|---|---|---|
| `[name]` | `[path]` | `[skill]` | active / superseded / draft | one-line description |
```

Rules:
- An output is anything created or modified by Claude during the project.
- Status moves: `draft` → `active` → `superseded`. Never silently delete an output — supersede it instead, and let Sub-C audit decide when it gets removed.
- "Produced by" names the skill that authored it (e.g. `the-architect`, `project-lifecycle`, `llm-council`). If only inline tools were used, write `inline (Bash/Read/Edit)`.

---

## 3. Artefacts index — `Outputs/artefacts_index.md`

A separate file in the project's `Outputs/` directory, regenerated on every handover update. Single source of truth for "what is in this project and what does it mean".

Format:

```markdown
# Artefacts Index — [Project Name]
**Generated:** [YYYY-MM-DD HH:MM]
**Project root:** `[Windows path]`
**Total artefacts:** [N inputs + M outputs]

## Inputs ([N])

- [`filename`](relative/path) — one-line description (≤ 120 chars)
- [`another`](relative/path) — one-line description

## Outputs — Active ([N])

- [`Final_Plan.md`](Final_Plan.md) — Council recommendation from the 2026-06-25 ROUTE-A run
- [`Premortem_Report.md`](Premortem_Report.md) — Six failure modes + risk register

## Outputs — Superseded ([N])

- [`Final_Plan_v1.md`](archive/Final_Plan_v1.md) — Initial council draft (superseded 2026-06-25 by Final_Plan.md)

## Outputs — Drafts ([N])

- [`docs/_draft_outline.md`](docs/_draft_outline.md) — Scratch outline, retain until §4b status flips

---

*Generated by `project-lifecycle` v1.2+. Regenerated on every handover update.*
```

Rules:
- **Clickable links** — every entry is a relative-path Markdown link from the index file's location.
- **Concise descriptions** — one line, ≤ 120 chars, must answer "what is this for?".
- **Three output buckets** — Active / Superseded / Drafts. Inputs are a single bucket.
- **Regen at close only** (v1.2.1 — council finding FM-L2-02). The index regenerates exclusively at Sub-D close, or when the user explicitly says "regen index" / "refresh artefacts index". It does NOT regenerate on every per-action / ultradian cadence tick — at high cadence that was 50× write amplification with no read-side benefit until close.
- **No atomic-rename needed** at close (single-writer, no concurrency). Plain write.

## 4. Telemetry log — `Outputs/_telemetry/log.md` (single file, append-only) — v1.3.0

**One file per project.** Created empty at kickoff. Every update appends a
new timestamped section. Never split into multiple files; never overwrite
prior sections.

Path: `Outputs/_telemetry/log.md` (single file)

### File structure

```markdown
# Telemetry Log — [Project Name]
**Created:** 2026-06-25T14:00
**Last appended:** 2026-06-25T18:30
**Total updates:** 3

> Append-only chronological log of every handover-update event. Most-recent
> entry is at the BOTTOM (chronological order). Sections are never edited
> in place; new entries are appended only.

---

## 2026-06-25T14:00 — kickoff
**Session ID:** [if known]
**Handover note updated:** yes — initial creation

### Skills used since last entry
*(first entry — empty)*

### Failure analysis
*(none — first entry)*

### Improvements plan
*(none — first entry)*

### Defining details for the next LLM
- Project root: [path]
- Initial cadence: end-of-session (default)

---

## 2026-06-25T15:00 — ultradian-tick
**Session ID:** [current]
**Handover note updated:** yes — §3, §4a, §7 refreshed

### Skills used since last entry

| Skill | Times invoked | Worked as intended? | Failures | Cause | Notes for future LLMs |
|---|---|---|---|---|---|
| coeus:project-lifecycle | 1 | Yes | 0 | — | Ultradian trigger fired cleanly |
| coeus:the-architect | 1 | Partial | 1 | Loaded by slash, but request was a diagnostic — should have routed to ROUTE D | Once v1.1 ROUTE D ships, re-classify to Yes |

### Failure analysis (≤ 5 items)

1. **Skill:** coeus:the-architect — **What failed:** mis-routed to ROUTE A — **Root cause:** auto-detect ambiguity — **Recommended improvement:** strengthen ROUTE D auto-detect patterns

### Improvements plan (Architect consultation if failures ≥ 1)

1. Strengthen ROUTE D auto-detect patterns — 10 min effort

### Defining details for the next LLM

- Routing surprise: the-architect fired on a diagnostic phrasing that should have gone direct to ROUTE D
- Worth grepping ROUTE D auto-detect patterns at next morph

---

## 2026-06-25T18:30 — session-close
**Session ID:** [current]
**Handover note updated:** yes — §3, §4, §4a, §4b, §7, §8 refreshed

[... same structure as above ...]
```

### Append rules

- **Append, never edit.** Existing sections are immutable history.
- **Most-recent at the BOTTOM** (chronological order; future LLMs read top-to-bottom). Update the file header's `Last appended` + `Total updates` fields on each append.
- **Timestamp format:** ISO-8601 (`YYYY-MM-DDTHH:MM`).
- **Reason** is one of: `kickoff` | `per-action` | `ultradian-tick` | `daily` | `milestone` | `custom-<spec>` | `audit` | `session-close`.
- **`Defining details for the next LLM` is mandatory** even when empty (`- (none this update)`).
- **Apply `_shared/uncertainty_rules.md`** — flag `[UNVERIFIED]` claims, hedged language on simulated voices.
- **No separate index file needed** — the log itself is chronological and self-indexing.

### Why a single log (v1.3.0 change)

Previous design (v1.2.1) wrote one file per update + a `_telemetry/index.md`
rollup at close. That created N+1 files when 1 file would do, and the rollup
itself was just a chronological index — exactly what an append-only log gives
for free. v1.3.0 collapses both into a single file. Reduces directory bloat,
removes the regen-rollup step from Sub-D close, removes the discovery-gap
problem (FM-L2-03) by construction.

## 5. When each piece fires (v1.3.0 — append-only telemetry log)

**One-time-create-at-kickoff files** (created once, then updated in place — never recreated, never timestamped-duplicated):

| File | Created at | Updated by |
|---|---|---|
| `[ProjectName]_LLM_Handover.md` (§4a Inputs, §4b Outputs, all sections) | Kickoff (Sub-K) | Every cadence-tick + close |
| `Outputs/artefacts_index.md` | Kickoff (Sub-K, empty buckets) | Sub-D close, Sub-C audit, or explicit "regen index" — NOT every cadence tick |
| `Outputs/_telemetry/log.md` | Kickoff (Sub-K, with first entry) | Every cadence-tick + close (append section, never recreate file) |

| Event | Inputs §4a | Outputs §4b | Artefacts index | Telemetry log |
|---|---|---|---|---|
| Kickoff | initialise empty | initialise empty | create (empty buckets) | create + append first entry |
| Handover update (cadence-triggered) | refresh | refresh | **deferred to close** (mark §9 dirty) | **append** new timestamped entry |
| Sub-C audit (manual) | unchanged | refresh status column | regenerate (in place) | append new audit entry |
| Sub-D close | refresh | refresh | regenerate (in place) | append session-close entry |

The artefacts index regenerates **in place** (overwrites the existing file)
at close/audit only — never timestamped-duplicated.

The telemetry log is **append-only** — new entries added at the bottom,
header `Last appended` + `Total updates` refreshed, prior entries
immutable. No new files are ever created in `_telemetry/` after kickoff.

## 6. Housekeeping order (load-bearing)

Per user's instruction (v1.2 morph): housekeeping runs **before** the
handover note is written, not after. Sub-D close protocol (v1.3.0):

1. **Sub-C audit + delete obsolete artefacts** (housekeeping FIRST)
2. **Refresh §4a Inputs / §4b Outputs** in the handover note
3. **Regenerate `artefacts_index.md` in place** (overwrite existing file)
4. **Append session-close entry to `_telemetry/log.md`**
5. **Update §3, §7, §8** in the handover note
6. **Run the Architect consultation if failures ≥ 1**
7. **Pop up the close summary + action menu to the user**

This ordering means the artefacts index is always **post-cleanup** — it
never contains references to files that were about to be deleted.

**No new files are created during close** — all writes are to pre-existing
files created at kickoff. This is the load-bearing simplification
introduced in v1.3.0.
