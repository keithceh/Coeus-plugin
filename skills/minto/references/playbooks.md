# Minto Playbooks — Applying the Pyramid to This User's Deliverables

> Doctrine lives in [doctrine.md](doctrine.md) (§ references below point there).
> These playbooks map the method onto the deliverable types this user actually
> produces (executive / subsurface-leadership work). Minto's own position: one
> method for all expository documents — email, memo, report, slide deck — the
> deliverable differs only at the presentation stage (§10). Each playbook is
> therefore: the reader + Question to assume, the SCQ skeleton, the Key Line
> shape, and the presentation-stage rules that bite.

## Universal pre-work (every deliverable)

1. Name the primary reader and their Question (§12). For mixed audiences
   (board + SteerCo + functional heads), structure for the most senior
   decision-maker; others read the support layers.
2. Write the Answer as one sentence before drafting anything (§1). If the
   Answer can't be written, the thinking isn't done — drop to bottom-up
   process or the problem-solving frame (§9, §11).
3. Run the 30-second test on the skeleton: introduction + Key Line alone must
   carry the whole message (§13).

## 1. Board / investment recommendation, decision memo

- Reader's Question is usually "should we approve X?" or "how do we get from
  R1 to R2?" — frame via the problem-definition story (§9): Opening Scene,
  Disturbing Event, R1 (undesired result), R2 (desired result).
- Answer = the recommendation, first. Key Line: inductive (§4) — 3–5 same-kind
  supports (e.g., value case, risk position, do-ability), each MECE-checked (§6).
- Alternatives the board already knows about go in the Complication, never as
  suspense at the end (§9, p. 135).
- Known strong disagreement with the conclusion is the ONE sanctioned reason to
  put argument before action (§15) — use deliberately, not by default.
- Every summary states an effect or implication — never "there are three
  considerations" (§7).

## 2. Gate / stage-gate review submission (G1–G3, kill/pivot reviews)

- Question: "has this phase earned passage to the next?" Answer first:
  PROCEED / PROCEED-CONDITIONAL / HOLD / KILL, then conditions.
- Situation = the gate criteria as agreed (noncontroversial, §5). Complication =
  what this phase found. Key Line: structural order mirroring the gate criteria
  (§8) — the MECE test lives here.
- Findings→conclusions discipline (§9): no finding that leads to no conclusion,
  no conclusion resting on no finding. Gate packs fail this test most often.

## 3. Stakeholder / leadership update (biweekly, monthly, milestone)

- The reader's standing Question: "are we on track, and what do you need from
  me?" Progress, cost, schedule, escalation, risk — the Answer summarizes state
  PLUS the ask, in the first lines (matches the user's existing BLUF habit —
  Minto's answer-first IS BLUF with a derivation discipline behind it).
- Key Line in degree order (§8): most consequential change first, not
  chronology. Chronology belongs in the introduction, if anywhere (§11).
- Updates repeat: the Situation can shrink to one sentence for a familiar
  reader (§13). Do not re-tell the project history every issue.

## 4. Playback deck / steering presentation (pptx or HTML)

- Storyboard from the pyramid BEFORE making any slide (§10). Text slides carry
  the pyramid's points — one point per slide, stark and terse; exhibits
  alternate with text slides.
- Transitional and introductory material goes in what is said aloud, not on
  slides; accept that the deck is not a standalone handout (§15). If a
  standalone pre-read is needed, that is a second deliverable (a memo), not a
  wordier deck.
- Slide titles are the Key Line assertions — never category labels
  ("Findings", "Update") (§7, §10).

## 5. Proposal / framing document / terms of reference

- Question: "should we do this, this way, with these resources?" Common
  introduction patterns from the book: directive, request for funds, letter of
  proposal (§5) — each an S-C-Q skeleton.
- Scope/approach/resourcing sections take structural order (§8); check the
  parts against the whole (MECE, §6).

## 6. Technical report / close-out / sign-off (basin studies, QC reports)

- The reader is rarely the analyst: the Question is "what did you conclude and
  can I rely on it?", not "what did you do?" Method and chronology go low in
  the pyramid or to appendices; time order only for genuine process steps (§8).
- Headings state ideas, not categories — "Reprocessing recovers the pre-stack
  signal", never "Results" (§7, §10). The document must read as prose with
  headings removed (§10).
- Citations stay in the sentences they support (user convention — compatible:
  Minto governs ordering, not evidencing).

## 7. Email / one-pager

- Same method, shrunk (§10): Situation can be one clause; Answer in the first
  sentence; underlined or bolded points instead of headings. If the email needs
  a scroll, it wanted to be a memo with a pyramid.

## 8. Reviewing an existing document (surgery mode)

- Minto's own working method (§14): draw the document's current structure as a
  pyramid; every failure of the three rules (§2) marks a cut point.
- Review order: (1) find the Answer — is it first? (2) does the introduction
  contain only what the reader will accept as true? (3) test each grouping:
  same kind? ordered by time/structure/degree? summarized by effect or
  implication, not a blank label? (4) 30-second test on intro + Key Line.
- Deliver the diagnosis as: current structure → rule violations → rebuilt
  pyramid → rewritten skeleton. Do not line-edit prose before the structure
  stands (the problem is the thinking, not the language — §14).
